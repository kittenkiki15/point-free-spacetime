RDF のトリプルでの索引は作れます。ナレッジグラフ化（knowledge graph）につながるように組み立てる案を考えました。

###### 検討の結果

- **トリプルを元にする**：索引の中身を「主語・述語・目的語」のトリプルとして組み立て、JSON と Turtle（RDF の書式）の両方をそこから出力します。逆引きのコマンドも同じトリプルから引きます。
- **最初の範囲は、ファイルにある構造**：次のようなトリプルにできます。
  - 種類：`D-0002 rdf:type 定義`
  - 名前：`rdfs:label "実際の実験と可能な実験"@ja`
  - 状態・層・初出の回・Issue
  - 依存・目標・参照：依存する、目標とする、参照する（依存ではない）
  - 予想・結果の関係
  - タスクの関係：前提のタスク、関係する ID、Q の親と割り当てたタスク
  - 結果と、Lean の定理名やテスト名との対応
- **場所の付いた言及**：言及は「どのファイルの、どの節の何行目か」を持つので、1 本のトリプルでは書けません。そこで、言及ごとに一つのノード（`_:m a 言及 ; 言及元 <ファイル> ; 言及先 D-0002 ; 節 "定義" ; 行 12`）を作ります。RDF 1.1 の範囲で書けるので、どの道具でも読めます。トリプルに属性を直接付ける RDF-star は、道具ごとの対応にまだ差があるので使いません。
- **循環の検査**：SPARQL のプロパティパス（`pfs:dependsOn+`）で、推移的な依存と循環を問い合わせられます。今の Python の検査と照合して、検査を二重に確かめることもできます。
- **本当の意味でのナレッジグラフ**：「D-0014 は D-0002 の一般化である」「この前提はこの論文の定理に当たる」のような、数学・物理の中身どうしの関係は、ファイルの構造からは自動では取り出せません。こうした関係は、述語の語彙（オントロジー、ontology）を設計して、人が判断して書く必要があります。今回の索引はその土台になります。

###### 決めていただきたいこと

**1. IRI（各 ID を指す名前）の付け方**
- **(a) 推奨**：公開リポジトリの `main` のファイルの URL（例：`公開リポジトリの `main` の `definitions/D-0002.md` を指す GitHub の URL`）にします。開けばその定義が見えます。基底の URL は 1 か所の定数にして、後で永続的な URL（w3id.org など）に移せるようにします。
- (b) `urn:pfs:D-0002` のような、開けない名前にします。ホスティングに依存しませんが、開いても中身は見えません。

**2. 語彙**
- **推奨**：一般的な語彙（`rdf:type`・`rdfs:label`・`dcterms` など）を使える所では使い、本プロジェクト独自の述語（依存・目標・参照・言及・状態・層など）は独自の名前空間 `pfs:` に置きます。語彙の定義も Turtle で `tools/` に置き、索引と一緒に読み込めるようにします。

**3. 範囲と道具**
- **推奨**：この回は、上の「最初の範囲」（ファイルの構造と言及）までにします。中身の関係のオントロジーは、新しいタスクとして `roadmap.md` に加え、別の回に扱います。
