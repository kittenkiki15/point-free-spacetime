# 対話ログの運用（詳細）

1 ターンごとの対話ログ（`tools/live_log.py`）の運用の詳細です。要点は [`CLAUDE.md`](../CLAUDE.md) の「対話ログ」にあります（第 32 回に、`CLAUDE.md` を短くするため、詳細をここに移した。T-0027 のリリース前の見直しでユーザーと決めた）。

セッションの状態の齟齬（ユーザーと Claude の認識するセッションの状態が食い違うこと）に備えて、1 ターンごとに発言とタイムスタンプを作業ブランチの対話ログに残す（第 28 回にユーザーが提案し、第 29 回に仕組みを決めた。T-0025 の 1）。

- **各応答の最初の操作と、最後の操作**で `python3 tools/live_log.py sync` を実行する（新しい回の最初の応答では、「セッションの始め方」の手順と `start` を先に行う。`start` が最初の同期を兼ねる。2 回目以降の応答では、最初に `sync` する）。最初の同期でユーザーの発言を、最後の同期で Claude の応答を残す。保証できるのは「次の同期までに記録された発言」である。最後の同期の後に書いた文は次の同期で保存されるので、本文を書いてから最後に同期し、同期の後には短い一文だけを置く。回の最後の文は、次の回の `start` が前の回のログを先に同期して残す（コンテナが失われて、セッション記録が残っていない場合は残らない）。
- ユーザーの発言のないターン（GitHub の通知などで起きたターン）では同期しない。ログの push が CI を動かし、その完了の通知でまた起きる、という繰り返しを避けるためである（第 29 回）。それまでの分は、次にユーザーの発言があったターンの同期で、まとめて残る。文脈が失われたと思われるとき（ユーザーの発言が、覚えのない提案を前提にしているときなど）は、先に `logs/` の対話ログを読んで、別の分岐のやりとりを確かめる。
- `sync` は、この作業ディレクトリのセッション記録（`/clear` などで分かれた複数のファイルを含む。ほかのプロジェクトの記録は読まず、`sync` を実行したと登録したセッションか、公開・非公開のリポジトリの下で作業したと確かめられたセッションの行だけを採る。確かめられないセッションの発言が期間の中にあれば、保留する。非公開側の `live-sessions.json` に、この研究の会話なら ID を、そうでなければ「!」を付けた ID を加えて確かめる）から、その回のログの全体を毎回作り直し、次のように置く。
  - 公開側の `logs/YYYY-MM-DD_NN_<話題>.md`：発言とタイムスタンプだけ（ツールの呼び出しと結果は含めない）。PR の作成からマージまでの発言も含める。
  - 非公開側の `logs/` の同じ名前のファイル：ツールの呼び出しを含む記録（ツールの結果は先頭だけに切り詰める。元のセッション記録そのものではない）。
- 前提：この作業ディレクトリ（コンテナ）では、この研究の会話だけを行う。`/clear` の後や、文脈が分かれた後の会話も、この研究の会話として記録に含める（分岐を記録に残すことが、この仕組みの目的の一つである）。別の会話をする場合は、別の環境で行う。
- push 先は作業ブランチ（`main` ではない）。ログは、セッションの終わりの PR で `main` に入る。ただし、前の回の PR がマージされた後に、次の回の `start` が回収した前の回の最後の発言は、次の回の PR で `main` に入る。公開側のログのコミットには `logs/` のファイルだけを含める（非公開側のログのコミットには、伏せ字・置き換えの設定とセッションの登録簿も含める）。非公開側（ログと、伏せ字・置き換えの設定の `redactions.txt`・`log-overrides.json`、セッションの登録簿の `live-sessions.json`）を先に push する。公開側で `logs/` 以外を変えた未 push のコミット（ふだんの作業）があるときは、`sync` は push しない（ふだんの push で先に送る）。非公開側は公開に当たらないので、この規則の対象外とし、未 push の作業のコミットもログと一緒に送る。push の前に、まだ push していない履歴の `logs/` の版も検査し、問題があれば push しない（その版を含むコミットを作り直してから、`sync` をやり直す）。push に失敗したら、その同期のコミットは取り消されるので、原因を直して `sync` をやり直す。
- 時刻かセッションのない発言（どの回のものか判定できない）や、セッション記録の読めない行があれば、`sync` は保留する。今のセッションの ID（環境変数 `CLAUDE_CODE_SESSION_ID`）が分からないときも保留する（推測はしない。`--session-id` で明示する）。
- セッション記録が失われる（コンテナの作り直しなど）と、作り直した版から保存済みの発言が消える。`sync` はその場合（本文が変わった場合を含む）に上書きせず、終了コード 1 で終わる（意図した置き換えなら `--allow-loss` を付ける）。次の回の `start` で、前の回のセッション記録が失われていた場合は、保存済みのログをそのまま残して新しい回を始める（最後の同期の後の発言は回収できない）。前の回の保存済みの発言の本文が変わる場合（伏せ字の語句の追加など）は、新しい回を始めない。前の回のログと、公開済みの履歴に直す前の版が残っていないかを確かめてから、やり直す。`start` は、回の情報（タイトルなど）を検査してから `logs/live.json` に書く。
- `sync` は、push の前に次を検査する。どれかに当たれば、公開側には書かず、非公開リポジトリの `held/` に保留して、終了コード 1 で終わる。
  - 伏せ字の照合（`redactions.txt` の語句。正規表現ではなく固定文字列として、大文字・小文字を区別せずに照合する）が 0 件であること。
  - 登録していない個人情報・秘密情報の形（メールアドレス、電話番号（区切りのないもの、空白で区切ったものを含む）、既知の形式のキー、32 文字以上の高エントロピーの文字列。ただし、英小文字・数字・区切り（`/`・`-`・`_`）だけからなり、区切りを含むものは、パスやファイル名と区別できないので除く）がないこと。まだ push していない履歴の `logs/` のファイル名も検査する。
  - 他者の文章の長い引用の疑い（長く続く引用のブロック、日本語をほとんど含まない長い段落。コードブロックの中も含む）がないこと。
  - ファイル名と `logs/live.json` も同じく照合する。話題（slug）は英小文字・数字とハイフンだけにする。
  - 自動の検査で見つかるのは、既知の形式と、形からの推定だけである。漏れがないことは保証しないので、気づいたものは `redactions.txt` に加える。
- 保留したときは、ユーザーに伝えて、確認してから公開する。
  - 個人情報の断片は、`redactions.txt`（非公開リポジトリ）に語句を追記して伏せ字にする。
  - 他者の文章の長い引用は、非公開リポジトリの `log-overrides.json` に、発言の識別子（保留のときに表示される。uuid か、uuid のない行は中身から作った `h-` で始まる値）と要約を `{"<識別子>": {"replace": "要約"}}` の形で書く。誤検出なら `{"<識別子>": {"approve": "理由"}}` と書く。途中に届いた発言には、同じ発言の通常の行の uuid での指定も当たる。
  - キーの形の高エントロピーの文字列の誤検出（URL の一部など）は、保留のときに表示されるハッシュ（`t-` で始まる値。文字列そのものは書かない）を使って、`{"<識別子>": {"approve_tokens": {"t-<ハッシュ>": "理由"}}}` と書く。その発言の中の、ハッシュが一致する文字列だけが通る（T-0027 の 2）。伏せ字の語句、メールアドレス、電話番号、既知の形式のキーは、承認では通らない。
- 個人情報の断片を、検索コマンドなどに直接書かない（非公開側の記録に残るため）。検索には `redactions.txt` を使う。
- 第 28 回までの対話ログは、セッションの終わりに `tools/export_log.py` で書き出したもの（PR を作るまでの対話）である。第 32 回に、公開側の版からツールの呼び出しの中身と結果を除き、要約の 1 行だけを残した（他者の文章の長い引用を避けるため。T-0027 の 3）。除く前の版（ツールの呼び出しを折りたたんで含む）は、非公開側の `logs/` に置いた。書き出し直さない（書き出し直すと、除いた中身が戻る）。
