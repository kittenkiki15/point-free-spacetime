1. **（第 29 回に完了）** 第 29 回に、`tools/live_log.py` で実装した（`CLAUDE.md` の「対話ログ」）。決めたこと（ユーザーの判断）：Claude が各応答の最初と最後に `sync` を実行する（フックは使わない。Claude Code の設定を書き換える操作が自己改変として自動の許可で拒否されたため。必要になったら、ユーザーが設定するフックに移る）。push 先は `main` ではなく作業ブランチとし、第 28 回の `main` への直接の push の例外は取り消した。公開側は発言とタイムスタンプだけ、ツールを含む全体は非公開リポジトリに置き、セッションの終わりの書き出しはやめた（案 A）。PR を作った後からマージまでの発言も残す。以下は第 28 回に書いた検討の記録：対話ログを 1 ターンごとにリモートの `main` に追記する（`CLAUDE.md` の「Git の運用」の例外）。発言とタイムスタンプだけを記録し、ツールの出力は含めない。push の前に毎回、伏せ字の処理と照合を機械的に行い、登録していない個人情報・秘密情報と長い引用を検出する検査も行う（疑いがあるか確かめられないターンは保留する。PR #51 のレビュー）。Claude Code のフックで自動化する案がある。ユーザーの発言をいつ保存するか（応答の前に文脈が失われた場合に備えて、発言を送った時点で保存するなど）と、逐次保存したログをセッションの終わりの書き出しと PR とで重複なく扱う方法を決める（PR #51 のレビューの詳細化の論点）。PR を作った後からマージまでの発言も保存するか（保存するなら、「セッションの終え方」の「ログに含めない」と README の説明を改める）も決める（PR #51 のレビューの詳細化の論点）。直接の push を `logs/` に限るため、最新の `origin/main` からログ専用の作業領域（作業ブランチとは別）を作り、push の前に、送るコミット全体の `origin/main` との差分が `logs/` の追記だけであることを検査する（作業ブランチの未マージのコミットが PR を経ずに `main` に入るのを防ぐ。PR #51 のレビューの詳細化の論点）。
2. **（第 30 回に完了）** [`tasks/`](../tasks/README.md) に移し、未完了の 15 件に Issue（#53〜#67）を作った。決めたこと（ユーザーの判断）：状態などの内容はファイルを正本とし、Issue には作業の進み具合と議論を置く。Issue は未完了のタスクだけに作る。以下は第 28 回に書いた検討の記録：タスクを 1 件 1 ファイル（例：`tasks/T-NNNN.md`）にし、GitHub の Issue で状態と対応した回を追跡する。状態の正本をファイルと Issue のどちらにするかと、もう一方との同期・検査の方法を決める（予想と同じく、ファイルを正本とする案がある。PR #51 のレビューの詳細化の論点）。`roadmap.md` には段階・順序・一覧表・図だけを残す。割り当て漏れの検査を、タスクのファイルを読むように直す。
