## 内容

第 31 回に、ID の依存関係と参照箇所の索引を RDF のトリプルで作った（`tools/id_index.py`、語彙は `tools/pfs.ttl`。T-0025 の 4）。この索引が表すのは、ファイルにある構造（種類・名前・状態・依存・目標・参照・タスクの関係・言及の箇所）だけである。ユーザーが関心を示した、本プロジェクトで扱う知識のナレッジグラフ（knowledge graph）化に向けて、数学・物理の中身どうしの関係を表す語彙を設計する（第 31 回にユーザーと決めた。別の回に扱う）。

- 中身の関係の例（Claude の案）：「一般化する・特殊化する」「同値である」「例・反例である」「〜の定理に当たる（文献）」「〜を仮定すると導かれる」。どの関係を置くかと、その意味（推移性など）を決める。
- 関係は、ファイルの構造からは自動で取り出せないので、人が判断して書く。書く場所（各ファイルの表の行か、別のファイルか）と、検査の方法を決める。
- 既存の語彙との対応を検討する：用語一覧の用語を `skos:Concept` に、文献を `references.bib` の引用キーに対応させるなど。
- IRI の基底は、今は公開リポジトリの `main` のファイルの URL である（`tools/id_index.py` の `BASE` と `tools/pfs.ttl` の接頭辞の 2 か所。変えるときは両方を改める）。永続的な URL（w3id.org など）に移すかを、必要になったときに決める。
- 索引の Markdown の読み取りは、このリポジトリで使っている書き方（インラインのリンク、囲み型のコードブロック、インラインのコード、見出し）に限っている（第 31 回にユーザーと決めた。PR #72 のレビューで、使っていない書き方への対応の指摘が続いたため）。字下げ型のコードブロック・自動リンク・HTML などは扱わない。範囲を広げる必要が出たら、正規表現から Markdown の構文解析器（例：`markdown-it-py`）に置き換える。
- 索引のファイルはコミットしない（第 31 回）。
- リンク先の確かめ方（PR #72 のレビューの詳細化の論点）：`link_target_id` は、リンク先の末尾のファイル名（`X-NNNN.md`）だけで ID へのリンクと判定し、ディレクトリ（`definitions/` など）は確かめない。表示文字が ID のリンクは、別の検査（`test_id_links_point_to_matching_files`・`tq_link_problems`）でディレクトリまで確かめている。説明付きのリンクも、ID に対応するディレクトリまで確かめるかを決める。
- 言及を集める範囲（PR #72 のレビューの詳細化の論点）：今は Markdown と `lean/`・`sim/` のコードで、`tools/` のコード（`tools/id_index.py` の T-0025 などの言及）は含めない。参照箇所の逆引きを道具のコードまで広げるかを決める。公開する Turtle が必要になったら、CI の成果物や GitHub Pages で出すかを決める。


**運用の道具の論点（第 33 回に [T-0027](T-0027.md) の「リリース後でよい論点」から移した。詳細化の論点）**

- タスクの再開（PR #68 のレビュー）：完了したタスクを再開する（状態を完了から戻す）手順を認めるかを決める。今の検査は、第 30 回の時点で完了していたタスク（`TASKS_DONE_BEFORE_ISSUES`）に、完了のまま「Issue なし」を許し、その完了を求める。再開を認めるなら、「この集合に含まれ、かつ状態が完了なら「なし」を許す」判定に改め、再開したタスクには Issue を作る。
- Q の状態と Issue（PR #68 のレビュー）：Q の状態と Issue の開閉の対応（例：未解決なら開く、解決・取り下げなら閉じる）と、状態を変えるときの更新の手順を決めて、`questions/README.md` と `CLAUDE.md` に書く。
- 引用の検査の範囲（PR #52 のレビュー）：長い引用の自動の検査は、引用記号が続く場合と、日本語をほとんど含まない長文が中心で、引用記号のない長い日本語の転載は見つからない（漏れを保証しないことは `CLAUDE.md` に明記した）。公開前に人が確認する条件や、出典を伴う長文を保留する条件を決める。
- ブランチ名の照合（PR #52 のレビュー）：`sync` は、公開・非公開のリポジトリの作業ブランチの名前を照合せず、それぞれ今のブランチに push する。取り違えを防ぐために push の前に一致を検査するかを決める。
- パスの形のキー（PR #52 のレビュー）：キーの疑いの検査は、英小文字・数字・区切り（`/`・`-`・`_`）だけからなる文字列をパスとみなして除くので、同じ形の未登録の秘密情報は通り得る（この限界は `CLAUDE.md` に明記した）。`key=` の値や、パスの各要素など、パス全体と分けて検査・保留する条件を決める。
- 承認の一連の確認（PR #73 のレビューの詳細化の論点）：`approve_tokens` のテストは `check_rows` の結果までを確かめている。今の版の検査は、発言ごとの確認を通した版として履歴の検査から除くので、承認は push まで効く。ただし、まだ push していない古い版が複数残っている場合は、古い版を承認なしで検査するので止まり得る。承認から push までの一連のテストを加えるかを決める。
- 公開側の文書の検査の範囲（PR #73 のレビューの詳細化の論点。`CLAUDE.md` の `tools/` の規則で見送ったもの）：`tools/tests/test_public_docs.py` は、表の中の ID のリンクだけのセルを、リンク先が `X-NNNN.md` で終わる相対パスなら検査から外す（リンク先のディレクトリの部分は確かめない）。また、本文だけを検査し、ファイル名は検査しない（対話ログはファイル名も検査する）。実際に起こる筋書き（リンク先のパスや公開ファイルの名前にキーやメールアドレスを書くこと）は見当たらないので、問題が起きたときに、リンク先を正規の ID のパスに限ることと、ファイル名の検査を加える。
- 公開側の文書の push 前の検査（PR #73 のレビューの詳細化の論点）：`tools/tests/test_public_docs.py` は CI で動くので、論文の本文などを誤って書いた Markdown を push すると、CI で気づいて直しても、その版は作業ブランチの履歴に残る（今回の写しと同じ筋書き）。対話ログの `sync` と同じように、push の前に、まだ push していない Markdown の各版を検査する仕組み（git の pre-push フックなど）を加えるかを決める。
- 承認と本文（PR #52 のレビュー）：`approve` は発言の識別子だけに結び付く。同じ識別子の本文が後から変わり得るなら、承認したときの本文のハッシュも照合するかを決める（上の 2 と合わせて扱える）。
